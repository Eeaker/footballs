# 最初 POC 管线与当前生产实现映射

本文用于说明老板最初提供的 `pipeline(1)(4).py` 与当前 Football Insight 产品化仓库之间的关系。最初脚本作为需求/算法基线保存于项目沟通材料中，不再复制进正式源码仓库，以避免同时维护两套主管线。

## 1. 原始 POC 四阶段

原始脚本的核心处理链为：

1. **Stage 1：检测 + 短时跟踪 + 外观特征**  
   YOLOv8 检测人/球，BoT-SORT 生成 tracklet，ResNet50 与颜色直方图累积 ReID 特征。
2. **Stage 2：全局重关联 + 出场过滤**  
   先剔除极短 tracklet，再依据外观/颜色与时间互斥关系合并，并按出场时长/占比限制最终全局 ID。
3. **Stage 3：可视化 + MOT**  
   仅对保留 ID 渲染追踪框并导出 MOT 文本。
4. **Stage 4：事件检测与切片**  
   以球加速度、方向变化和球员速度为代理信号检测关键动作，导出事件索引，并按事件类型分层抽样切片。

## 2. 当前生产模块映射

| POC 能力 | 当前 canonical 实现 | 说明 |
|---|---|---|
| 人/球检测与短时跟踪 | `engine/tracking/` | 保留检测、BoT-SORT/追踪、技术 ID 主职责，并加入场内过滤与质量门控 |
| 全局 ID / 低出场过滤 | `engine/tracking/` | 仍保留短轨迹与低出场过滤思路；生产参数以当前引擎/产品配置为准 |
| ReID/身份稳定性 | `engine/tracking/` + `engine/identity_audit/` | 身份审计作为独立质检层，不无痕改写上游事实 |
| MOT 与追踪可视化 | `engine/tracking/` | MOT 是后续米制、OCR、事件和审计的基础事实 |
| 球运动/关键事件 | `engine/tracking/` + `engine/match_analysis/` | 从单一代理分数扩展为球权、传球、语义事件与高光链路 |
| 事件切片 | 产品层高光/结果服务 | 正式产品按目标高光与结果中心统一输出 |
| 场地尺度 | `engine/football_metric_running/` | POC 未覆盖；生产链增加多锚点动态 Homography 与米制门控 |
| 号码/真实身份 | `engine/match_analysis/` + 人工复核 | POC 未覆盖；生产链区分机器候选与人工确认 |
| 报告/2D 回放 | `app/` + `engine/match_analysis/` | POC 未覆盖；生产链提供正式报告、球员卡和唯一米制 2D 回放 |

## 3. 必须保留的基线约束

产品迭代不能破坏以下原始约束：

- 极短轨迹应在全局身份处理前过滤，避免噪声和候选组合爆炸；
- 低出场/背景人员不能无限进入最终技术 ID 集合；
- 被剔除的 ID 不应继续进入 MOT、渲染或事件速度信号；
- 事件抽样要避免只取同一种动作；
- 帧域、`vid_stride` 与时间换算必须保持一致，不能产生二次 stride；
- 机器候选结果必须与人工确认语义区分。

## 4. 参数差异

POC 中曾使用：

- `max_ids=35`
- `min_track_frames=10`
- `min_presence_ratio=0.01`
- `imgsz=1280`
- `event_percentile=92`
- `event_min_gap=2.0s`
- `pre_sec/post_sec=3.0/2.0s`

当前产品层默认配置已经根据正式比赛制式、动态标定和场内过滤做了扩展；例如当前使用 `expected_players`、草地/脚点门控以及更完整的标定参数。参数调整必须以 [`调参清单.md`](调参清单.md) 和当前代码为准，不允许为了“与旧脚本一致”而直接覆盖生产配置。

## 5. 单一主管线原则

生产系统只保留一个总编排入口：`app/services/pipeline.py`。原始 POC、模块 CLI、验收脚本都不应成为第二套生产编排。新增功能应接入现有阶段和数据契约，而不是复制旧管线再平行演进。
