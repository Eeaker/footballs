# 仓库使用规范（全员必读）

本规范适用于正式源码仓库及其 Gitee 镜像。目标是保证代码可追溯、可复现，同时避免比赛素材、球员数据、模型和密钥进入版本历史。

## 1. 分支与合并

1. `main` 作为稳定主线，不直接承载临时实验。
2. 日常开发使用 `dev-姓名缩写` 或 `feature/*` 分支；发布/交付整理使用 `release/*` 分支。
3. 合并到稳定主线前必须完成自测并保留测试命令与结果；团队流程允许时通过 PR 合并。
4. 交付到外部/镜像仓库前必须从已整理的 release 分支制作**无历史污染的源码快照**，不要把曾包含 Demo/真实数据的 Git 历史整体镜像过去。

## 2. Commit message

统一格式：

```text
[模块] 改动内容 — 原因
```

示例：

```text
[tracking] 统一事件时间戳帧域 — 避免二次 stride
[docs] 补齐正式部署与验收说明 — 上线交付
```

提交说明必须回答“改了什么”和“为什么”，禁止长期使用 `update`、`fix`、`test` 等无法追溯的描述。

## 3. 数据与文件红线

以下内容一律不得提交：

- 比赛视频、球员照片/名单及其他真实业务素材；
- `tracks_mot*`、`tracking_mot*`、事件索引、切片、热力图、运行日志和报告等运行产物；
- Demo/参考比赛数据；
- 模型权重或推理引擎（`.pt/.pth/.onnx/.engine`）；
- `.env`、Token、私钥、账号密码等敏感信息；
- Python 虚拟环境、缓存和依赖下载目录；
- 单文件大于 10 MB 的非源码文件。

如误传上述内容，不能只做一次删除提交；必须停止继续传播，并按仓库管理员要求清理/重写受污染历史。

## 4. 大文件与外部资产

需要共享的模型、视频、离线依赖包等放到公司批准的文件存储。交付文档至少登记：文件名、版本/用途、获取位置、SHA256（适用时）和负责人。

## 5. 参数变更

任何生产参数变更都必须同步更新 [`调参清单.md`](调参清单.md)，记录默认值、影响范围和确认状态。不得只改代码不改参数登记表。

## 6. 发布前最低检查

```bash
python -m compileall -q app engine scripts
python scripts/audit_engine_chain.py
python scripts/verify_product.py
```

如果当前环境具备对应依赖，还应运行各模块 pytest。发布快照还必须检查：无 `demo_data/`、无禁入扩展名、无敏感文件、无单文件 >10 MB。

## 7. 本地副本

项目交付或离开项目时，按公司数据管理要求清理本地比赛素材、运行结果、模型缓存和临时导出；源码副本是否保留以公司权限与资产管理制度为准。
