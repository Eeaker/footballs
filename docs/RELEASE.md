# 正式发布与 Gitee 镜像

本文规定正式源码包与代码镜像的最低门禁。目标是只交付可维护的生产源码，不把 Demo、业务数据、模型、密钥或受污染 Git 历史带入目标仓库。

## 1. 发布来源

正式交付必须从已完成自测的 `release/*` 分支生成，不直接从开发中间态打包。

发布快照应是**源码快照**：只包含当前有效文件，不携带此前曾经包含 Demo/业务数据的大对象历史。Gitee 镜像需要保留开发历史时，应先确认历史从未包含红线数据；否则使用新的根提交。

## 2. 必须排除

- `demo_data/` 与任何参考比赛结果；
- `runtime/`、`outputs*`、`clips/`、MOT、事件索引、日志、报告等运行产物；
- 比赛视频、球员素材/名单等业务数据；
- 模型权重和推理引擎；
- 虚拟环境、缓存、离线 wheelhouse；
- `.env`、Token、私钥、密码；
- 单文件 >10 MB 的非源码交付物。

## 3. 最低验证

```bash
python -m compileall -q app engine scripts
python scripts/audit_engine_chain.py
python scripts/verify_product.py
```

具备完整依赖时补充全部 pytest 与 Windows 启动器检查。真实新比赛的 AI 全链路验收仍按 `ACCEPTANCE.md` 执行，不能用历史结果或 Demo 代替。

## 4. 快照检查建议

发布脚本至少执行：

1. `git ls-files` 获取受控文件；
2. 拒绝任何路径包含 `demo_data`；
3. 拒绝禁入扩展名/敏感文件；
4. 拒绝单文件 >10 MB；
5. 生成文件数量、总体积、源 commit、SHA256 清单；
6. 生成 ZIP 供归档；
7. 如推送 Gitee，使用一个干净新仓库/孤儿分支提交快照，避免把被删除的数据历史一起推过去。

## 5. Gitee 目标

公司 Gitee 仓库按指定个人/交付分支接收源码快照。推送前先确认目标分支，禁止覆盖 `main` 或其他成员分支。若目标分支已经存在旧骨架，正式交付允许在明确授权后以新的干净根提交替换该个人分支。

## 6. 发布记录

每次正式发布应记录：

- 源 GitHub 仓库与 release 分支；
- 源 commit SHA；
- Gitee 仓库与目标分支；
- 文件数量与未压缩体积；
- 是否包含 Demo：必须为 0；
- >10 MB 文件数量：必须为 0；
- 基础验证结果；
- 真实新素材 GPU 验收状态；
- 发布人/日期。
